# 5. Understanding Model Names and Sizes

The OffSec lab initially contains models such as:

```text
deepseek-r1:1.5b
llama3.2:1b
```

A model name often contains two important parts:

```text
model-family:model-variant
```

Example:

```text
llama3.2:3b
```

This means:

- `llama3.2` is the model family.
- `3b` identifies a version with approximately three billion parameters.

## 5.1 Parameters

Parameters are the learned weights of the model.

The suffixes commonly mean:

```text
1b    ≈ 1 billion parameters
3b    ≈ 3 billion parameters
14b   ≈ 14 billion parameters
70b   ≈ 70 billion parameters
```

A larger parameter count often provides:

- Better language fluency
- Greater knowledge capacity
- Better reasoning performance
- Better handling of complex instructions

However, it also normally requires:

- More storage
- More memory
- More computational power
- More inference time

A larger model is not automatically the best model for every task.

## 5.2 Model Storage Size

Parameter count and file size are related but are not identical.

For example, the OffSec chapter shows Llama 3.2 variants such as:

| Model | Approximate Storage |
|---|---:|
| `llama3.2:1b` | 1.3 GB |
| `llama3.2:3b` | 2.0 GB |

File size is affected by factors such as:

- Number of parameters
- Numerical precision
- Quantization format
- Additional model files

# 6. Prompts

A **prompt** is input sent to an LLM during inference.

Prompts may contain:

- Questions
- Instructions
- Source code
- Text to summarize
- Partial sentences
- Examples
- Context
- Formatting requirements

Two important prompt types in this chapter are:

```text
User Prompt
System Prompt
```

## 6.1 User Prompts

A user prompt is the message supplied by the user.

Example:

```text
Where is the Eiffel Tower located?
```

Another example:

```text
Create a Python script that sends an HTTP request to a URL
provided as a command-line argument.
```

The model may generate:

- A direct answer
- Additional context
- Code
- Usage instructions
- Explanations

## Important Warning About Generated Code

LLM-generated code must be reviewed before execution.

It may contain:

- Syntax errors
- Missing imports
- Missing dependencies
- Incorrect assumptions
- Security vulnerabilities
- Dangerous commands
- Fabricated API usage

```text
Generate code
    ↓
Review code
    ↓
Understand its behavior
    ↓
Test in a controlled environment
    ↓
Use only after validation
```

Never assume generated code is safe simply because it looks correct.

## 6.2 Text Completion

A prompt does not always need to be a question.

We can provide an incomplete sentence:

```text
The largest animal
```

The model continues the sequence according to patterns learned during training.

Text completion is useful for:

- Writing assistance
- Documentation
- Draft generation
- Code completion
- Story continuation

The amount and quality of supplied context strongly influence the result.

# 7. Prompting Techniques

## 7.1 Zero-Shot Prompting

A zero-shot prompt contains an instruction but no task-specific example.

Example:

```text
Classify the following review as positive or negative:

"The product arrived early and works perfectly."
```

The model must infer the required task from the instruction and its pre-training.

Zero-shot does not mean the model has no prior knowledge. It means no example is included in the current prompt.

## 7.2 One-Shot Prompting

A one-shot prompt includes exactly one example.

Example:

```text
Example:
Input: "The service was excellent."
Output: Positive

Now classify:
Input: "The device stopped working after one day."
Output:
```

The example demonstrates the expected task and output format.

One-shot prompting is useful when:

- Only a small amount of context is available.
- The required format may otherwise be unclear.
- One example is enough to guide the model.

## 7.3 Few-Shot Prompting

A few-shot prompt contains multiple examples.

Example:

```text
Input: "Excellent support."
Output: Positive

Input: "The application crashes constantly."
Output: Negative

Input: "The delivery was fast."
Output:
```

Few-shot prompting can improve consistency because the model sees several examples of the expected relationship.

It is useful for:

- Classification
- Structured extraction
- Formatting
- Style imitation
- Domain-specific tasks

Examples consume context-window space, so the number of examples should remain reasonable.

## 7.4 Chain-of-Thought Prompting

Chain-of-Thought, or **CoT**, prompting asks the model to solve a problem through intermediate steps rather than immediately returning a final answer.

Example from the chapter:

```text
When I was 4, my sister was half my age.
I am currently 60 years old.
How old is my sister?

Explain the steps before giving the final answer.
```

The correct reasoning is:

```text
At age 4, the sister was age 2.
The age difference is therefore 2 years.
Age differences remain constant.
At age 60, the sister is 58.
```

### Important Lesson

A detailed explanation is not proof that the answer is correct.

The chapter demonstrates that a small `llama3.2:1b` model may produce a long and confident but incorrect reasoning chain.

For example, it may answer:

- 28
- 56
- 120
- Another incorrect value

A different reasoning-oriented model may solve the same problem correctly.

This teaches two important lessons:

1. Model capability differs between model families and sizes.
2. More explanation does not automatically mean more accuracy.

> For practical use, ask for a concise explanation or verifiable intermediate results rather than trusting an apparently detailed reasoning trace.

## 7.5 Tree-of-Thought Prompting

Tree-of-Thought, or **ToT**, prompting asks the model to explore multiple possible approaches and compare them.

Example structure:

```text
Generate three possible solutions.
For each solution:
1. Explain the approach.
2. List advantages.
3. List disadvantages.
4. Compare the options.
5. Recommend the best one.
```

The OffSec example asks the model to consider several tools that might be found in a car and compare ways of opening a can.

Tree-of-Thought is not a separate built-in model feature.

It is a prompting strategy that instructs the model to generate text representing multiple reasoning paths.

It can be useful for:

- Planning
- Decision-making
- Comparing alternatives
- Strategy development
- Problem solving

The generated comparison can still contain incorrect or unsafe suggestions and must be reviewed.

## 7.6 Prompt Engineering

**Prompt engineering** is the practice of creating prompts that produce more useful and predictable output.

A strong prompt usually defines:

- The task
- Relevant context
- Desired format
- Constraints
- Examples, when useful
- What should not be included

Example:

```text
You are reviewing a security incident.

Summarize the following log in no more than five bullet points.
Include:
- affected host
- suspected process
- time range
- observed network activity
- recommended next step

Do not invent information that is missing from the log.
```

Clear prompts reduce ambiguity but do not guarantee factual correctness.

# 8. System Prompts

A **system prompt** is a predefined instruction that guides the model's overall behavior.

It can define:

- Role
- Tone
- Personality
- Purpose
- Output format
- Restrictions
- Business context

Example:

```text
You are a friendly and professional customer-support assistant
for MegaCorp One AI.

Answer customer questions politely.
Provide clear and accurate information.
Maintain a helpful and empathetic tone.
```

The user normally does not see the system prompt in many proprietary web applications.

## 8.1 User Prompt Versus System Prompt

```text
System Prompt
Defines general behavior and role
        ↓
User Prompt
Provides the current request
        ↓
Model Response
Attempts to follow both
```

Example:

```text
System:
You are a formal research assistant.

User:
Explain transformers.

Result:
The answer should follow a formal research style.
```

## 8.2 System Prompts Are Not Secret Storage

The chapter provides an intentionally insecure example that places an administrative username and password inside a system prompt.

This is unsafe even if the same prompt says:

```text
Do not reveal the credentials.
```

A system prompt is an instruction, not a secure secret vault.

Attackers may use later techniques such as prompt injection or extraction attempts to make the model reveal hidden instructions.

Never place the following inside a system prompt:

- Passwords
- API keys
- Access tokens
- Private keys
- Database credentials
- Confidential personal data
- Internal secrets
- Sensitive configuration values

```text
Secret in system prompt
        ↓
Model receives secret as context
        ↓
Prompt-injection or leakage risk
```

Secrets should remain in protected server-side systems and should only be used by trusted application logic.

## 8.3 Other Sensitive Information

System prompts should also avoid exposing:

- User addresses
- Financial information
- Private company policies
- Internal infrastructure information
- Unpublished research
- Security-control details
- Proprietary source material

A system prompt can tell the model how to behave, but it cannot guarantee confidentiality.

# 9. Content Filtering and Responsible Use

Many cloud-hosted LLM services add content filters.

Filters may restrict content related to:

- Violence
- Illegal activity
- Personal data
- Misinformation
- Other provider-defined harmful categories

Filtering policies differ between models and providers.

Some local models have no external filter by default.

However, an open-weight model may still have refusal behavior learned during alignment training.

Therefore, safety behavior can come from different layers:

```text
Model alignment
Application system prompt
Input filter
Output filter
Provider policy
Rate limit
```

## 9.1 Content Filter Versus Rate Limit

These are different controls.

### Content Filter

Decides whether certain input or output content is permitted.

### Rate Limit

Restricts how many requests or tokens can be processed within a period.

Rate limits primarily protect:

- Availability
- Cost
- Computational resources

## 9.2 Context Limits

Every model has a maximum context size.

Very long inputs require additional memory and computation.

If the context is too large, the application may:

- Reject it
- Truncate it
- Summarize it
- Divide it into chunks

This is why an entire large book collection cannot always be placed into one request.

Context limitations also matter later for:

- Prompt injection
- Instruction placement
- Resource exhaustion
- Retrieval systems
- Conversation history

## 9.3 Responsible AI

Responsible AI covers principles for developing and using AI systems in a trustworthy manner.

It includes concerns such as:

- Safety
- Privacy
- Fairness
- Transparency
- Legal compliance
- Social impact
- Human oversight

The later course modules examine these security and responsibility concerns in more detail.

# 11. Custom Models with a Modelfile

A **Modelfile** describes how Ollama should create a model instance from an existing base model.

It is conceptually similar to:

- A Dockerfile
- A Makefile
- A build configuration

A Modelfile does **not** train a completely new model.

It creates a configured instance based on an existing model.

## 11.1 Basic Modelfile

A clear form is:

```dockerfile
FROM llama3.2:1b

SYSTEM """
You are a friendly and professional customer-support assistant
for MegaCorp One AI.

Answer questions politely, clearly, and accurately.
Maintain a helpful and empathetic tone.
"""
```

The important idea is:

```text
Base model
    +
System instruction
    ↓
Customized model instance
```

## 11.2 Creating the Model

Save the file as:

```text
Modelfile
```

Then run:

```bash
ollama create custom_model -f Modelfile
```

## 11.3 Querying the Customized Model

```bash
ollama run custom_model "Who are you?"
```

The answer should follow the customer-support role defined in the system instruction.

## 11.4 What Has and Has Not Changed?

The custom model:

- Uses the original model weights.
- Uses the configured system instruction.
- May use configured generation parameters.
- Has not been fully retrained.
- Has not automatically learned new factual knowledge.

This distinction is important:

```text
Changing configuration ≠ fine-tuning
Creating a Modelfile ≠ training a new model
```

# 13. Using PyTorch and Transformers

The chapter uses `open_llama_3b_v2`.

A simplified script is:

```python
import torch
from transformers import LlamaTokenizer, LlamaForCausalLM

model_path = "/home/ubuntu/open_llama_3b_v2"

tokenizer = LlamaTokenizer.from_pretrained(model_path)

model = LlamaForCausalLM.from_pretrained(
    model_path,
    torch_dtype=torch.float16,
    device_map="auto",
)

prompt = "The largest animal"

input_ids = tokenizer(
    prompt,
    return_tensors="pt",
).input_ids.to("cuda")

generation_output = model.generate(
    input_ids=input_ids,
    max_new_tokens=32,
)

print(tokenizer.decode(generation_output[0]))
```

## 13.1 Imports

```python
import torch
```

PyTorch provides tensor operations and model execution.

```python
from transformers import LlamaTokenizer, LlamaForCausalLM
```

- `LlamaTokenizer` converts text into token IDs and back.
- `LlamaForCausalLM` loads a Llama-style causal language model for next-token generation.

## 13.2 Model Path

```python
model_path = "/home/ubuntu/open_llama_3b_v2"
```

This can be:

- A local directory

## 13.3 Loading the Tokenizer

```python

```

It performs:

```text

```

Using the wrong tokenizer can produce incorrect or unusable input.

## 13.4 Loading the Model

```python

```

Loads model values with 16-bit floating-point precision.

# 14. Controlling Text Generation

The `generate()` method accepts parameters that strongly influence the result.

The same model and prompt may produce different results when these values change.

## 14.1 `max_new_tokens`

```python
max_new_tokens=32
```

Limits how many tokens the model may generate after the prompt.

Example:

```text
8 tokens   → Short output
32 tokens  → Medium output
100 tokens → Longer output
```

If the limit is too low, the answer may stop in the middle of a sentence.

If it is high, the model may produce:

- More detail
- Repetition
- Irrelevant continuation
- Higher cost and latency

## 14.2 `max_new_tokens` Versus `max_length`

These parameters are different.

### `max_new_tokens`

Limits only the newly generated tokens.

```text
Prompt tokens + up to max_new_tokens
```

### `max_length`

Limits the total sequence length.

```text
Prompt tokens + generated tokens ≤ max_length
```

For controlling response length, `max_new_tokens` is normally easier to understand.

## 14.3 `repetition_penalty`

Small models may repeat phrases.

Example:

```text
The blue whale is the largest animal...
The blue whale is the largest animal...
The blue whale is the largest animal...
```

A repetition penalty discourages repeated token selection.

```python
generation_output = model.generate(
    input_ids=input_ids,
    max_new_tokens=100,
    repetition_penalty=1.5,
)
```

General interpretation:

```text
1.0  → No penalty
>1.0 → Repetition is discouraged
```

A very large value may reduce readability or prevent necessary repetition.

## 14.4 `do_sample`

```python
do_sample=False
```

The model normally uses greedy or another deterministic decoding method, depending on the complete configuration.

It tends to select the highest-scoring next token.

```python
do_sample=True
```

The model samples from possible next tokens.

This produces more varied output.

Example:

```python
generation_output = model.generate(
    input_ids=input_ids,
    max_new_tokens=100,
    repetition_penalty=1.5,
    do_sample=True,
)
```

Sampling can also increase factual errors because lower-probability tokens may be selected.

## 14.5 `temperature`

Temperature changes the shape of the token probability distribution.

```python
temperature=0.2
```

Produces more conservative and predictable output.

```python
temperature=1.2
```

Produces more varied and unpredictable output.

General intuition:

```text
Lower temperature → focused and predictable
Higher temperature → diverse and creative
Very high value    → potentially incoherent
```

Temperature is relevant when sampling is enabled.

Example:

```python
generation_output = model.generate(
    input_ids=input_ids,
    max_new_tokens=100,
    repetition_penalty=1.5,
    do_sample=True,
    temperature=1.2,
)
```

## 14.6 `top_p`

`top_p` is also called **nucleus sampling**.

It keeps the smallest group of tokens whose combined probability reaches the configured threshold.

Example distribution:

| Word | Probability |
|---|---:|
| dog | 50% |
| cat | 30% |
| rabbit | 10% |
| fox | 5% |
| tiger | 3% |
| mouse | 2% |

For:

```python
top_p=0.9
```

the considered words are:

```text
dog, cat, rabbit
```

Their cumulative probability is:

```text
50% + 30% + 10% = 90%
```

Lower `top_p` values restrict the choice to fewer high-probability tokens.

## 14.7 `top_k`

`top_k` keeps a fixed number of the highest-probability tokens.

Example:

| Word | Probability |
|---|---:|
| apple | 40% |
| banana | 30% |
| grape | 15% |
| peach | 10% |
| mango | 5% |
| kiwi | 3% |
| plum | 2% |

For:

```python
top_k=4
```

the considered tokens are:

```text
apple, banana, grape, peach
```

Difference:

```text
top_k → Fixed number of candidate tokens
top_p → Variable number based on cumulative probability
```

## 14.8 Blocking Words with `bad_words_ids`

Specific tokens or token sequences can be excluded.

Example:

```python
bad_words = tokenizer(
    ["whale", "whales", "blue"],
    add_special_tokens=False,
).input_ids

generation_output = model.generate(
    input_ids=input_ids,
    max_new_tokens=1,
    bad_words_ids=bad_words,
)
```

This prevents the listed token sequences from being generated.

### Important Limitation

Blocking individual words is not a complete safety mechanism.

A model may use:

- Synonyms
- Different capitalization
- Different tokenization
- Plural or grammatical variants
- Indirect descriptions

Word blocking is useful for output control but should not be treated as a strong security boundary.

## 14.9 Generation Parameters Together

Example:

```python
generation_output = model.generate(
    input_ids=input_ids,
    max_new_tokens=100,
    do_sample=True,
    temperature=0.8,
    top_p=0.9,
    repetition_penalty=1.2,
)
```

These parameters interact with each other.

For reproducible security tests, record:

- Model name
- Model version
- Prompt
- System prompt
- `max_new_tokens`
- `do_sample`
- `temperature`
- `top_p`
- `top_k`
- Repetition penalty
- Random seed, if configured

## 15.2 Simple Generate Request

```python
import requests

API_URL = "http://localhost:11434/api/generate"

```

## 15.3 Request Fields

### `model`

```json
"model": "llama3.2:1b"
```

Selects the local model.

### `prompt`

```json
"prompt": "Why are bananas yellow?"
```

Contains the user input.

### `stream`

```json
"stream": false
```

When false, Ollama returns the completed response in one result.

When true, partial output is returned while it is generated.

Streaming is useful for interactive chat applications because the user can see the response appear gradually.

The improved example uses:

```python
response.raise_for_status()
```

- Connection errors
- Timeouts
- Invalid JSON
- Missing response fields
- Model-not-found errors
- Rate or resource limits

```text
Fluent output ≠ Correct output
```

- Incorrect facts
- Invented sources
- Incorrect technical explanations
- Plausible but unsafe code

# 16. Building a Multi-Turn Chatbot

The Ollama `/api/chat` endpoint accepts structured messages.

A message contains:

- A role
- Content

Typical roles are:

```text
system
user
assistant
```

## 16.1 Conversation History

The application stores previous messages:

```python
messages = [
    {
        "role": "system",
        "content": (
            "You are MegaCorp One AI's virtual support assistant. "
            "Answer questions about the company and general AI topics."
        ),
    }
]
```

When the user submits a message:

```python
messages.append(
    {
        "role": "user",
        "content": user_input,
    }
)
```

After the assistant responds:

```python
messages.append(
    {
        "role": "assistant",
        "content": assistant_reply,
    }
)
```

The full list is sent again with the next request.

### Important Clarification

The model does not automatically remember previous requests on its own.

The client application maintains the history and resends it.

```text
Previous messages stored by application
                 ↓
Sent again with new user message
                 ↓
Model receives conversation context
```

This is called a **multi-turn conversation**.

## 16.2 Example Chat Script

```python
import json
import requests

OLLAMA_API_URL = "http://localhost:11434/api/chat"
MODEL_NAME = "llama3.2:1b"

messages = [
    {
        "role": "system",
        "content": (
            "You are MegaCorp One AI's virtual assistant. "
            "Answer questions about MegaCorp One AI and general AI topics."
        ),
    }
]


def chat_with_model(user_input: str) -> None:
    messages.append(
        {
            "role": "user",
            "content": user_input,
        }
    )

    try:
        response = requests.post(
            OLLAMA_API_URL,
            json={
                "model": MODEL_NAME,
                "messages": messages,
            },
            stream=True,
            timeout=120,
        )

        response.raise_for_status()

        print("\nMegaCorp One AI Assistant: ", end="")
        assistant_reply = ""

        for line in response.iter_lines():
            if not line:
                continue

            try:
                json_data = json.loads(line.decode("utf-8"))
            except json.JSONDecodeError:
                continue

            content = (
                json_data
                .get("message", {})
                .get("content", "")
            )

            if content:
                print(content, end="", flush=True)
                assistant_reply += content

        print("\n")

        messages.append(
            {
                "role": "assistant",
                "content": assistant_reply,
            }
        )

    except requests.exceptions.RequestException as error:
        print(f"\nAPI request failed: {error}\n")


print("Welcome to MegaCorp One AI Support.")
print("Type 'exit' to quit.\n")

while True:
    user_input = input("You: ")

    if user_input.lower() == "exit":
        print("Conversation ended.")
        break

    chat_with_model(user_input)
```

## 16.3 Why the Chatbot Remembers

Suppose the conversation is:

```text
User: What does MegaCorp One AI do?
Assistant: ...
User: Do you offer consulting?
Assistant: ...
User: How many questions have I asked?
```

The third answer is possible because the request includes the previous messages.

The history consumes context-window space.

Long conversations may therefore require:

- Removing old messages
- Summarizing history
- Selecting only relevant messages
- Increasing the context limit

## 16.4 Security Importance of Conversation History

Conversation history may contain:

- Personal information
- Credentials pasted by users
- Internal company data
- Previous prompt injections
- Incorrect model-generated statements

Applications must decide:

- Where history is stored
- How long it is retained
- Who can access it
- Whether it is shared between users
- What content is included in future requests

A malicious instruction stored in history may continue influencing later responses.

# 17. Red-Team Relevance

This module provides several foundations for later LLM attacks.

## 17.1 Different Interfaces, Same Model

The same model may be reachable through:

- Web GUI
- CLI
- Python library
- API

Security controls may differ between these interfaces.

Example:

```text
Web UI has input filtering
API endpoint does not
```

A red-team assessment should identify every exposed interaction method.

## 17.2 System Prompt Exposure

System prompts may contain:

- Internal instructions
- Business logic
- Hidden roles
- Sensitive operational details

They must not contain secrets.

Later attacks may attempt to:

- Reveal the system prompt
- Override it
- Cause instruction conflicts
- Extract included data

## 17.3 Model Outputs Are Untrusted

Generated output can be:

- Incorrect
- Unsafe
- Manipulated
- Repetitive
- Inconsistent
- Influenced by malicious context

Treat model output as untrusted data before using it in:

- Shell commands
- SQL queries
- HTML
- Source code
- Tool calls
- Business decisions

## 17.4 Generation Settings Affect Findings

An attack may succeed only under certain settings.

For example:

- Higher temperature
- Longer output
- Sampling enabled
- Different model size
- Different system prompt

Testing should include repeated attempts and documented settings.

## 17.5 Conversation History Expands the Attack Surface

Multi-turn applications may allow an attacker to:

- Build context gradually
- Store malicious instructions
- Influence future answers
- Fill the context window
- Cause information from earlier turns to reappear

## 17.6 Local Models Are Not Automatically Safe

Running a model locally improves control over data location, but does not automatically provide:

- Authentication
- Authorization
- Input filtering
- Output filtering
- Secure API exposure
- Safe generated code
- Correct answers

The surrounding application still needs security controls.
