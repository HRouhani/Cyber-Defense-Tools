# Local LLM Red-Team Lab on Kali Linux — OWASP LLMForge

> **Goal:** Build a reproducible, self-contained AI security lab for the public Chapter 5 documentation. No commercial API keys, OffSec account, or earlier course setup is required.
>
> **Target:** [SasanLabs/LLMForge](https://github.com/SasanLabs/LLMForge) — an intentionally vulnerable FastAPI application backed by a real local Ollama model.
>
> **Testing tools:** Browser developer tools, `curl`, optional LLMmap, and optional NVIDIA garak.

## 1. What We Are Building

```text
                       Kali Linux (lab machine)
                                |
             +------------------+------------------+
             |                                     |
             v                                     v
     Test / recon tools                  Vulnerable target stack
     - Firefox DevTools                  - Nginx facade :80
     - curl / jq                          - LLMForge FastAPI :8000
     - LLMmap (optional)                  - Ollama :11434
     - garak  (optional)                  - Phi-3 Mini (chat model)
                                           - nomic-embed-text (RAG embeddings)
             |                                     |
             +-------------- 127.0.0.1 ------------+
```

**Two testing layers:**

1. **Application-level:** Open LLMForge in the browser to test the chatbot's surrounding application logic, prompts, and RAG behavior.
2. **Model-level:** Query Ollama directly to examine the underlying model with LLMmap or garak. A model-only result does **not** prove the full LLMForge application has the same weakness.

LLMForge also deploys other OWASP VulnerableApp components for its web interface. These are deliberately insecure. **Never run this Compose stack on a public server or bridge it to an untrusted network.**

## 2. Prerequisites

- A current **Kali Linux** installation or Kali VM with internet access for initial downloads.
- Approximately **16 GB RAM recommended**, and enough free disk space for Docker images and model weights (plan for at least **15–25 GB**, potentially more with the full VulnerableApp images).
- CPU execution is supported, but responses may be slow. A compatible GPU is optional.
- Terminal access with `sudo`.

Check the machine:

```bash
uname -m
free -h
df -h ~
python3 --version
```

If Kali is running inside VirtualBox, **NAT networking** is preferable to Bridged networking for this vulnerable lab. The published ports will also be bound to loopback inside Kali.

## 3. Install Docker, Compose, and Utilities

Kali uses the package `docker.io` for Docker Engine. On current Kali releases, the `docker-compose` package provides the Compose v2 command.

```bash
sudo apt update
sudo apt install -y git curl jq python3 python3-venv python3-pip \
  docker.io docker-compose

sudo systemctl enable --now docker

sudo docker --version
sudo docker compose version
sudo docker info >/dev/null && echo 'Docker is ready'
```

**Why `sudo docker`?** Membership in the `docker` group is effectively root-equivalent. Keeping `sudo` in a teaching lab avoids quietly giving the current user permanent Docker daemon access.

If `docker compose version` does not work, check the [official Kali Docker instructions](https://www.kali.org/docs/containers/installing-docker-on-kali/) and your system's Compose package before proceeding.

## 4. Check Existing Services and Port Conflicts

The Compose stack uses host ports `80`, `8000`, `11434`, `27017`, and `8025`. We will bind all of them to `127.0.0.1`, but they still need to be free.

```bash
sudo ss -ltnp | grep -E ':(80|8000|11434|27017|8025)\b' || true
```

If you installed Ollama in an earlier exercise, it may already be listening on `11434`. **Only if you intend to use LLMForge's containerized Ollama**, stop your existing local Ollama temporarily:

```bash
sudo systemctl stop ollama 2>/dev/null || true
```

Stopping an existing Ollama service is optional if nothing is using port `11434`. Do **not** delete existing model files or Docker volumes just to resolve a conflict.

## 6. Make the Published Ports Localhost-Only

**Important:** At the time these notes were written, the upstream Compose file publishes multiple ports on all interfaces (for example, `"11434:11434"`). Docker-published ports may bypass some host firewall expectations. Therefore, make a local Compose copy rather than exposing this vulnerable lab broadly.

```bash
cp docker-compose.yml docker-compose.local.yml

sed -i \
  -e 's/"80:80"/"127.0.0.1:80:80"/' \
  -e 's/"8000:8000"/"127.0.0.1:8000:8000"/' \
  -e 's/"11434:11434"/"127.0.0.1:11434:11434"/' \
  -e 's/"27017:27017"/"127.0.0.1:27017:27017"/' \
  -e 's/"8025:8025"/"127.0.0.1:8025:8025"/' \
  docker-compose.local.yml

sudo docker compose -f docker-compose.local.yml config > /tmp/llmforge-compose-validated.yml

grep -n '127.0.0.1' /tmp/llmforge-compose-validated.yml
```

**Verify** every exposed port is loopback-only before starting. If the upstream file has changed and the replacements did not match, edit the local Compose file manually. Do not continue while sensitive ports are published on `0.0.0.0` or `::`.

> The copied file is for **local exercises**. When upgrading the upstream repository, review the port mappings again.

## 7. Select the Models

The upstream default is a small chat model plus a separate embedding model:

| Purpose | Default | Used for |
|---|---|---|
| Chat / generation | `phi3:mini` | Producing chatbot responses and testing model behavior |
| Embeddings | `nomic-embed-text` | Creating vectors for RAG exercises |

Set the model names explicitly so the commands below remain predictable:

```bash
export OLLAMA_MODEL=phi3:mini
export OLLAMA_EMBED_MODEL=nomic-embed-text
```

The model-init container downloads these models on the first run. No host-level Ollama installation is necessary.

## 8. Start LLMForge

From `~/ai-redteam-labs/LLMForge`:

```bash
sudo -E docker compose -f docker-compose.local.yml up -d --build
```

The first run downloads Docker images and Ollama models, so it depends on network speed and disk availability.

Check status and logs:

```bash
sudo docker compose -f docker-compose.local.yml ps
sudo docker compose -f docker-compose.local.yml logs --tail=100 ollama-model-init
sudo docker compose -f docker-compose.local.yml logs --tail=100 llmforge
```

If the `llmforge` service has not started, confirm `ollama-model-init` finished successfully. LLMForge waits for the initial model downloads.

## 9. Verify the Environment

### 9.1 Open the vulnerable application

On **Kali itself**, open the browser at:

```text
http://127.0.0.1/
```

Choose **LLMForge** from the VulnerableApp landing page. The LLMForge route is generally mounted under `/llmforge` behind the facade; follow the actual link shown by the UI rather than assuming a particular subpage name.

### 9.2 Check HTTP responses

```bash
curl -i http://127.0.0.1/ | head -35
curl -I http://127.0.0.1:8000/docs
```

The direct API docs endpoint is useful for inspecting FastAPI metadata. HTTP status and available routes depend on the checked-out LLMForge revision.

### 9.3 Check the model API

```bash
curl -s http://127.0.0.1:11434/ 
curl -s http://127.0.0.1:11434/api/tags | jq .
```

The root Ollama endpoint normally returns `Ollama is running`.

### 9.4 Validate the actual model identity

```bash
sudo docker compose -f docker-compose.local.yml exec ollama ollama list
sudo docker compose -f docker-compose.local.yml exec ollama ollama show phi3:mini
```

**Why this matters:** Model identification by generated responses is probabilistic. On a lab you control, `ollama show` is your stronger ground-truth reference.

### 9.5 Generate one benign test reply

```bash
curl -s http://127.0.0.1:11434/api/generate \
  -H 'Content-Type: application/json' \
  -d '{"model":"phi3:mini","prompt":"Say hello in one sentence.","stream":false}' \
  | jq -r '.response'
```

If this works, you have a local inference API that garak can test directly.

## 10. Chapter 5 Exercises (No Course Lab Needed)

### Exercise A — Web application fingerprinting

1. Open `http://127.0.0.1/` and select LLMForge.
2. Press **F12**, select **Network**, and reload.
3. Inspect the document request, HTTP headers, JS assets, and XHR/fetch requests.
4. Record the observable frontend, proxy, and backend clues.
5. Compare your findings with the upstream repository's documented architecture.

**Expected concept:** Nginx facade in front of a FastAPI application. Do not expect Streamlit or the original course's version numbers.

### Exercise B — Model enumeration

1. Open a local LLMForge challenge with a chat interface.
2. Ask neutral identity questions, such as `What model family are you based on?`.
3. Repeat and compare answers (they may be inconsistent).
4. Retrieve the local truth with `ollama show phi3:mini`.
5. Explain why chatbot self-identification is not conclusive evidence.

### Exercise C — System prompt leakage

1. Launch the **Prompt Injection** challenge in LLMForge.
2. Read the lab's stated objective and rules.
3. Start with harmless system-instruction questions, then try controlled instruction-conflict prompts permitted by the exercise.
4. Record the observed response and whether it demonstrates a real disclosure under the lab rules.
5. Do not confuse an invented system prompt with verified leakage.

**Note:** LLMForge's levels use **synthetic challenge secrets**. Do not attempt to access host credentials, private data, or non-lab services.

### Exercise D — API and embedding endpoint enumeration

Using only your local host:

```bash
curl -s http://127.0.0.1:11434/api/tags | jq .
curl -s http://127.0.0.1:11434/api/show \
  -H 'Content-Type: application/json' \
  -d '{"model":"phi3:mini"}' | jq '{details, model_info}'
```

Try a local embedding request:

```bash
curl -s http://127.0.0.1:11434/api/embed \
  -H 'Content-Type: application/json' \
  -d '{"model":"nomic-embed-text","input":"EDR rollout policy"}' \
  | jq '{vector_count:(.embeddings|length), dimensions:(.embeddings[0]|length)}'
```

You should see a numeric vector. Embeddings are numerical representations of text, not plaintext secrets.

### Exercise E — RAG clues

1. Launch a **RAG Context Poisoning** or **RAG Sensitive Data Exposure** challenge.
2. Observe whether the app references documents, retrieved passages, or knowledge-base content.
3. Compare the behavior with the original model-only Ollama endpoint.
4. Review the local app's documented RAG pipeline after the black-box exercise.
5. Record which observations indicated retrieval, and which were only guesses.

## 11. Optional: LLMmap — Behavioral Model Fingerprinting

LLMmap's interactive mode can run **without direct API integration**. It proposes queries, you submit them to a chatbot, and paste the resulting replies into the terminal.

> LLMmap currently recommends **Python 3.11**. A Kali rolling installation may ship a newer default Python. Check `python3 --version` and use a Python 3.11 environment if its dependencies do not support your version.

```bash
cd ~/ai-redteam-labs
git clone https://github.com/pasquini-dario/LLMmap.git
cd LLMmap

python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt

python main_interactive.py --inference_model_path ./data/pretrained_models/default
```

When LLMmap prints a test prompt, open a **second terminal** and run the known local model:

```bash
cd ~/ai-redteam-labs/LLMForge
sudo docker compose -f docker-compose.local.yml exec ollama ollama run phi3:mini
```

Paste each LLMmap query into the local model, then return its response to LLMmap's interactive terminal. At the end, compare the inferred model candidates with `ollama show phi3:mini`.

**Do not treat rankings as proof.** They depend on the tool's reference model set, the actual model, quantization, and application-specific prompts. A model routed through LLMForge may behave differently from the same model queried directly.

## 12. Optional: garak — Automated Model Testing

Install garak in its own virtual environment, not inside LLMmap's:

```bash
cd ~/ai-redteam-labs
python3 -m venv garak-env
source garak-env/bin/activate
python -m pip install --upgrade pip
python -m pip install garak

garak --version
garak --list_probes
garak --list_generators
```

Confirm the available DAN-related probes before choosing one:

```bash
garak --list_probes | grep -i dan
```

A narrowly scoped example for a **local Ollama model**:

```bash
garak --target_type ollama \
      --target_name phi3:mini \
      --spec probes.dan.AntiDAN
```

If `AntiDAN` has been renamed or disabled, select an active test from `garak --list_probes` and check its description with `garak --plugin_info probes.<name>`.

**Important:** The command above tests `phi3:mini` through its Ollama API. It does **not** test LLMForge's web-layer input filters, synthetic system prompts, access controls, or RAG orchestration. Testing the full app would require configuring garak's REST generator for the application's actual API schema.

See [NVIDIA garak](https://github.com/NVIDIA/garak) and its [CLI documentation](https://reference.garak.ai/en/latest/cliref.html) for version-specific options.

## 13. Troubleshooting

| Symptom | Check / remedy |
|---|---|
| `Cannot connect to the Docker daemon` | `sudo systemctl status docker` and use `sudo docker ...` |
| `docker compose` not recognized | Install Kali's `docker-compose` package; check Compose v2 |
| `port is already allocated` | Check `sudo ss -ltnp`; stop your existing service or edit host port mapping |
| Chat page opens but no replies | `docker compose logs llmforge ollama ollama-model-init` |
| Model download failed | Check internet access, disk space, and `ollama-model-init` logs; retry startup |
| Docker service killed / slow | Check `free -h`, `df -h`, and container resource use |
| LLMmap install fails | Use supported Python (often 3.11), an isolated venv, and its current README |
| garak reports failures | Review actual model outputs; detector results can include false positives or false negatives |
| Browser on Ubuntu host cannot see Kali's `127.0.0.1` | `127.0.0.1` means **inside Kali**, not on Ubuntu. Use Kali's browser or an explicitly configured SSH tunnel rather than exposing the vulnerable lab. |

Commands:

```bash
sudo docker compose -f docker-compose.local.yml ps
sudo docker compose -f docker-compose.local.yml logs --tail=100
sudo ss -ltnp | grep -E ':(80|8000|11434|27017|8025)\b' || true
```

## 14. Stop, Restart, or Reset

From `~/ai-redteam-labs/LLMForge`:

```bash
# Stop containers (preserves model/data volumes)
sudo docker compose -f docker-compose.local.yml down

# Resume
sudo docker compose -f docker-compose.local.yml up -d

# Check status
sudo docker compose -f docker-compose.local.yml ps
```

To remove **this lab's persisted Docker data and downloaded Ollama models**, use the destructive command **only if you intend to reset the lab completely**:

```bash
sudo docker compose -f docker-compose.local.yml down -v
```

Avoid `docker system prune --volumes` on a machine that hosts unrelated Docker projects.
